- **The failure mode D2 looked for didn't happen.** A node's clock wait (the `Decider`'s `by(deadline)`) runs under the
  plan task's activity holder, which LangGraph's internal tasks inherit through the context. The token is given up
  while the timer waits and taken back when it fires, so `settle()` reaches zero. No worker thread is used: every node
  is `async`.
- **This harness has one cancel path.** Stop, leave, a cap pause and end all reach it the same way, through the
  runtime cancelling the turn task. Task 3.4 re-runs each of them through the real runtime.
- **Decision:** LangGraph stays (doc 01 A1). Phase 2 builds on it.
- **Found when the planner was wired (task 3.2): the same failure, one level up.** The turn worker awaited its plan task
  while keeping its own activity token. With Jev parked, the clock could never settle (`SettleTimeout` naming the
  `turns:` holder). LangGraph wasn't involved: the cause was the runtime waiting on another runtime task. Fixed with
  `vclock.join(task)`, which gives the caller's token up while it waits and takes it back only if the caller is still
  waiting, with unit tests for both paths. Check 2's cases are re-run through the real runtime in task 3.4.

**Finding: Stop can break the database writer (fixed after M9; see "The fix" below).** Both failures follow a Stop.
Offline, a task cancelled a **second time** while its write transaction is rolling back leaves the single writer
connection hung or closed ("Connection closed", "no active connection"); a single cancel is safe (330 trials). Which
code path cancels twice in the live run isn't pinned yet: a direct repro of the coalescer's `settle_timer` pattern came
out clean, 0 of 60. A real user pressing Stop can hit the same thing. Most likely it predates M9; the latency suite is
just the first run to Stop 100 times in a row.

#### The fix (`fix/stop-db-writer`, 2026-10-13)

**What breaks.** Two layers, both needed (each was tested alone against the storm tests below):

1. **A cancel inside a statement.** SQLAlchemy treats `CancelledError` as a disconnect: it invalidates the connection
   and closes it right there, inside the cancelled task (`terminate()` → a shielded graceful close). A second cancel
   cuts that wait short, so SQLAlchemy also force-stops the aiosqlite connection. aiosqlite's worker thread ends at the
   first stop it reads, and every call queued behind it (the graceful close's own stop, the pool's reset) waits
   forever. That is the hang of run 1. A connection still mid-transaction when it is abandoned keeps SQLite's write
   lock, which is the "database is locked" of run 2.
2. **A cancel inside BEGIN, COMMIT or ROLLBACK, or the pool's reset** (these run in SQLAlchemy's own context
   managers and pool code, outside the statement path).

**The changes:**
- `db/engines.py`: a `handle_error` listener sets `is_disconnect = False` for `CancelledError` (SQLAlchemy's documented
  hook). For aiosqlite that is the truth: a cancelled await doesn't stop the statement, which finishes on the
  connection's own thread, and the ROLLBACK queued next runs after it. The connection stays sound.
- `db/uow.py`: `write()` and `read()` run BEGIN, and the end (COMMIT or ROLLBACK, then the connection back to the
  pool), through the new `vclock.to_the_end`. That runs a step as its own task, tracked for virtual time, and keeps
  waiting through any number of cancels before re-raising one. The writer lock is let go only once the connection is
  back in the pool. A cancel that lands in a COMMIT is re-raised after it, and the committed events are still
  published (events go out if and only if they were stored).
- Three places that passed a second cancel on are fixed at the source. They are real patterns, but which one fired in
  the live runs isn't proven (below):
  - `settle_timer` in `turn.py` awaited the coalescer's timer directly, so a Stop cancelling the turn cancelled the
    timer a second time, in its token write; `_stream`'s handler then cancelled it a third time.
  - `actor._cut_worker` awaited the worker directly, so `actor.stop()` cancelling the Stop command reached the worker
    a second time. It also swallowed the command's own cancel.
  - `EventWriter.append` reloads the session state after a failed write; a second cancel there left uncommitted events
    in memory, and every later seq off by their count. The reload now runs to the end.

**Tests** (offline, no network):
- `tests/integration/test_cancel_writes.py`, four "storm" tests that cancel a task on every loop turn until it ends:
  a body cancelled 60 times over, a storm starting anywhere in 199 short writes (published if and only if stored), a
  reader storm (the TRUNCATE checkpoint still succeeds afterwards) and a failing body. On the old code the first three
  **hang** (killed at 60 s, every time); with only the `handle_error` listener, the 199-write storm still hangs.
- `tests/sessions/test_stop_idle.py`: Stop pressed twice at once, 15 times, in real time while tokens arrive every
  7 ms. A last reply still completes, and the log reduces. This one passes on the old code too, so it guards the path
  without reproducing the bug.
- **Not reproduced:** a deterministic version of the `settle_timer` path (the timer's write held in BEGIN by another
  connection, then a big chunk, then Stop) hung the old code on 1 of its first 2 tries, then passed the next 12. So
  the exact live trigger stays unproven, and that test was not kept. The fix doesn't depend on it: any number of cancels anywhere in a read or write is now safe.
- Cost: a write or read takes ≈ 0.05 ms longer (p50 0.96 ms against 0.90 ms, 400 of each).

### What M9 found

1. **Jev picks the face well, but with low confidence.** On the 8 faces its confidence quartiles are 0.36 / 0.58 /
   0.75, while its picks are mostly right. So B5's floor grid (0.5–0.9) only removed right answers. Both emotion and
   reactions use **floor 0.2** (D36). Emotion meets E8 on English: 21/25 = 0.84, +0.40 over "always keep".
2. **Reactions are the weak spot.** Shown the listener's face, Jev copied it (83/90). With the face hidden, it chose
   `none` too often. On a fresh set labelled blind it reaches English 17/30 = 0.57 against the 0.80 target, still
   +0.27 over "always none" and far above today's random reactions (≈ 0.24). It ships at 0.2 by the user's choice
   (D39); the miss is recorded.
3. **The mood line doesn't help.** Across 34 non-neutral English turns: exact match +0.00, pairwise 0.51
   (unvalidated), and more replies naming the feeling (5/34 against 2/34). It is off by default (D40,
   `persona.moodLine`), and `agent` sends `agent-1`'s bytes.
4. **The 1:1 path is fast enough.** First word p50 1216 ms, p90 1427 ms (NFR-01: 2 s / 4 s). The face always came
   before the first word (NFR-29). Jev's turn plan took p50 453 ms, and its deadline fired on 1.7 % of turns.
5. **Stop could break the database writer** (9.6; fixed after M9 on `fix/stop-db-writer`, "The fix"). Two latency
   runs died just after a Stop, one hung and one failed with "database is locked". Offline, a second cancel during a
   write's rollback hangs or closes the single writer connection. The live code path that cancels twice isn't pinned.
   Real users press Stop, so this mattered beyond evals.
6. **The response store can't measure order bias.** The key sorts JSON keys, so the reversed-order request reads
   the first order's stored answer. Order bias is "not measured" (D38). Live calls aren't affected.
7. **`judge_pairwise` fails B4** (26/30, rule 0.90) at v1 and v2. Its misses are persona-swap pairs whose "known
   winner" isn't clean. `judge_names_feeling` v2 passes (0 false alarms).
