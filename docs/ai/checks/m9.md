## The LangGraph dependency (task 1.1, design D1)

- **Chosen:** `langgraph==1.2.12` (released 2026-09-21), the newest release at least two weeks old on 2026-10-12
  (1.2.13 and 1.2.14 were newer).
- **Its own dependencies are two weeks old too.** A first try with a global `--exclude-newer 2026-09-28` also
  downgraded packages already locked (SQLAlchemy 2.1.3 → 2.1.1 and four others), so it was undone. Instead,
  `[tool.uv] exclude-newer-package` limits only the five new packages that had newer releases: `jsonpatch` 1.33,
  `jsonpointer` 3.1.1, `langchain-core` 1.6.5, `langgraph-sdk` 0.4.5 and `tenacity` 9.1.4. No package that was
  already locked changed version.
- **It pulls in:** `langchain-core`, `langchain-protocol`, `langgraph-checkpoint`, `langgraph-prebuilt`,
  `langgraph-sdk`, `ormsgpack`, `jsonpatch`, `jsonpointer` and `tenacity`, plus `langsmith` (already locked by M7's
  `tracing` group, now always installed).
- **Used:** the graph runner only. No LangChain model classes (A8), no checkpointer (A9), LangSmith off (B11).
- **`langsmith` is now always installed** (a dependency of `langchain-core`). Nothing is sent unless the user opts in:
  M7's `guard_env()` forces every tracing switch off without `HORIZON_LANGSMITH=1`, and a graph run is wrapped in
  `no_trace()`. The opt-in-tracing spec's "missing install" case can no longer happen on its own; its delta says so.
- **The user's OK:** 2026-10-12, "Yes, install 1.2.12".

## Doc 01 checks 1 and 2 (tasks 1.4–1.7, design D2): **pass**

Run offline ($0) on Windows, 2026-10-12, with `langgraph` 1.2.12, on the plan graph `state → ask → decide → route`
(design D3). Test: `backend/tests/integration/test_plan_graph_checks.py` (`pytest -s` prints the figures).

| Check | Pass mark | Result |
|---|---|---|
| 1, overhead | < 50 ms (p95 difference) | graph p50 1.59 ms, p95 1.98 ms; the same nodes as plain calls p95 0.02 ms; **difference 1.95 ms** |
| 1, settling | every advance settles; identical repeats; nothing busy | 100 runs × 2 with Jev answering at 0.1–1.0 s: all settled, identical outputs and outcomes, `Activity.busy` empty; 30 runs answered past the 700 ms deadline and fell back (outcome `late`), 70 on time |
| 2, Stop during the plan | gone ≤ 500 ms; nothing left; the request still settles | cancelled with the decision parked: no reply chunk, nothing busy after release, the decision's outcome `cancelled` |
| 2, Stop during the reply | the same | cancelled mid-stream: nothing busy, the plan's decision `on_time`, the reply cut short |

- **The failure mode D2 looked for didn't happen.** A node's clock wait (the `Decider`'s `by(deadline)`) runs under the
  plan task's activity holder, which LangGraph's internal tasks inherit through the context. The token is given up
  while the timer waits and taken back when it fires, so `settle()` reaches zero. No worker thread is used: every node
  is `async`.
- **This harness has one cancel path.** Stop, leave, a cap pause and end all reach it the same way, through the
  runtime cancelling the turn task. Task 3.4 re-runs each of them through the real runtime.
- **Decision:** LangGraph stays (doc 01 A1). Phase 2 builds on it.
- **Found when the planner was wired (task 3.2): the same failure, one level up.** The turn worker awaited its plan task
  while keeping its own activity token. With Jev parked, the clock could never settle (`SettleTimeout` naming the
  `turns:` holder). LangGraph wasn't involved: the cause was the runtime waiting on another runtime task. Fixed with
  `vclock.join(task)`, which gives the caller's token up while it waits and takes it back only if the caller is still
  waiting, with unit tests for both paths. Check 2's cases are re-run through the real runtime in task 3.4.
