## The paid runs: results (phase 10)

### 10.1 The watch histories

Run `20261013T113502-watch-history-84cddb` (19:35 KL, off-peak; `naive` through the store, 0 store hits; the run folder
holds `.keep`). Estimate $0.0262; **spent $0.0569** (Meridian $0.0506 for 100 replies, Sunny Hollow $0.0063 for 40).

| History | Character lines | Notes | Tokens in the lines | Summary drops |
|---|---|---|---|---|
| `evals/watch/meridian_long.json` | 100 | 2 (turns 35, 70) | ≈ 7,240 | 0 |
| `evals/watch/sunnyhollow.json` | 40 | 1 (turn 20) | ≈ 2,890 | 0 |

Read in full before commit. Both scenes stay in character, take up each director's note on the next turn and keep all
three characters awake (naive's order is round-robin). Meridian ends in two long good-night loops (turns 18–35 and
82–100), which `talk_finished` and the steer are for. Naive's output is kept exactly as written, including what a
reader would fix: lines cut off at the reply's token limit (Meridian 88–90 are "Ad", "Adjourned. The court",
"…at a surviv"), a leaked `<!-- maybe cut -->` (Sunny Hollow 7), a stray `\` (Sunny Hollow 4) and `[n]` citation
markers in watch lines.

**Finding: no summary drop.** Naive's watch lines average about 70 tokens, so 100 turns came to about 7,240 tokens,
under watch's 9,000-token window; D23 had assumed about 10,000. The recaps see inputs up to about 7,200 tokens and no
rolling summary; the summary-in-recap path stays covered offline (`tests/sessions/test_recap.py`). The user chose to
accept and record this rather than re-run Meridian at about 130 turns (≈ $0.09).

**Finding: the estimate was 2.2× low.** Only 12 % of Meridian's input tokens were cache hits (Sunny Hollow 52 %),
where the plan assumed a warm prefix. The prompt is cache-friendly: two consecutive prompts of one character are
byte-identical through the persona and the history, and only the tail moves (the retrieved passages sit just before
the newest line). Most calls cached only their first 256 tokens, and one late call cached 5,376, so the misses come
from OpenRouter routing DeepSeek across providers, not from the prompt. The user approved going on at the corrected
estimates (latency watch ≈ $0.03, free run watch ≈ $0.05, free run group ≈ $0.03), each run capped near 2.5× its plan.

**`who_scene`'s languages:** both histories are English, so D23's "English 52, others 8" can't come from them. The
user chose all 60 English (non-English isn't scored for accuracy; `who_first` and `who_second` carry 20 non-English
items between them).

### 10.2 The watch who-speaks part and the recap items

`evals/datasets/who_speaks/who_scene.jsonl`: 60 cuts (Meridian 36, Sunny Hollow 24), each the live cast plan's state
after the k-th character line, labelled blind in `scene.py` after reading both histories. Every item has two
candidates (the characters who didn't just speak) and exactly one acceptable name; all English. The id prefix comes
from the same test-minimum search as the group parts: `wsc1`, giving dev 40 and test 20. The delegated review took
two passes (`evals/reviews/m10-review.md`): pass 1 found 2 disagreements, so the whole set was relabelled under the
rule's explicit reading (a direct address or question outranks a mention); pass 2 found 1, replaced. The
round-robin baseline scores 27/40 on dev and 11/20 on test; it was 16/20 on test before the relabel, which the
review discloses.

The 10 recap items now build from the histories (`RECAP_POINTS`: Meridian 20–100, Sunny Hollow 10–40). Checks:
`corpus-check` 0 problems, `overlap` 0 problems over 1,436 items, the builders are deterministic (the new
`test_the_watch_part_is_built_from_the_committed_histories` and `test_the_ten_recap_items_come_from_the_histories`).
