**Search timing (task 6.3).** On a test database holding 3,000 pieces for one character, every one with a stored
vector, and a worst case where every query word is in every piece (`test_search_timing_m12.py`, 110 searches each):

| Search | p50 | p99 |
|---|---|---|
| keywords only (no query vector) | 30 ms | 46 ms |
| keywords and two dense texts | 56 ms | 69 ms |

The target was 50 ms at p99. What costs, measured step by step:
- each flat KNN over the partition is ≈ 11 ms (two dense texts: 22 ms);
- the 20 stored vectors MMR compares cost ≈ 19 ms;
- FTS costs ≈ 9 ms;
- MMR itself costs ≈ 2 ms, after making it incremental.

Reading a vector back from sqlite-vec is the slow part:
- by key, ≈ 1.5 ms each;
- as an `IN` list, ≈ 20 ms (a partition scan);
- with the KNN query, +19 ms;
- as one statement of key lookups (what ships), ≈ 19 ms for 20.

Dense searches miss the target by about 20 ms. The test guards keyword searches at 50 ms and dense ones at 100 ms
until the user decides.

**1. Query embeddings from Malaysia miss the 400 ms wait (the deep path).**
- **The measurement** (the main run's ledger, 157 `query_embed` calls to Qwen3 Embedding 8B on Nebius): 907 ms at the
  fastest, **1,125 ms at the median**, 3.3 s at the p90, 4.8 s at the p97, and 16.2 s once.
- **The consequence:** D11 waited at most 400 ms from when the search needs the vector, so **94 of 107 dev deep
  turns ran on keywords only**.
- **What the dense half is worth:** dev Recall@8 was 0.90 on the mostly keyword-only main run, against 0.95–0.96 on
  the arms that had their vectors.
- **The user's choice (2026-10-15): start early and wait 800 ms.**
  - The 1:1, cast (group) and follow plans start the user message's embedding with Jev call 1, for a candidate with
    vectors (`deep.start_early_embedding`). gather's request for the same text joins it through the embedder's
    in-flight de-duplication, so it is still one call per message.
  - The agent path waits up to `retrieval.agent.queryEmbedWaitMs` = 800 ms; naive and scripted keep the top-level
    400 ms.
  - This reverses D-100's "never before the gate". A quick turn to an indexed speaker now costs one ≈ $0.000002
    embedding.
  - Watch and debate still start at the gate: their deep text isn't the plan's text, and their deep work already runs
    ahead of the turn.
  - Check 2 measures what the wait costs at the first word.

**2. A space on another provider could never embed (a product bug).**
- The embeddings client pinned its configured provider (Nebius) on every request and ignored the space's own provider.
  So `bge-m3@1024+h` (DeepInfra) got 404 on every call: its space was built empty, and the arm ran on keywords.
- `horizon space build` to any space on another provider would have failed the same way.
- **Fixed:** the space's provider rides through the embedder, the gateway and the client. The configured provider is
  the default, so the default space's store keys are unchanged.

**3. The order-only arms waited with live timing (the harness).**
- An arm got its vectors only when the query texts were already in the store from the main run. So:
  - the 2048-dimension and old-instruction spaces, whose query texts were new, ran on keywords;

- The arms were measuring the store, not the ranking.
- **Fixed:** an arm (D23: retrieval order only; timing is check 2's) waits for its query embeddings in full

- The main run keeps live timing and now starts its embedding before its own nouls call, as live starts it beside Jev
  call 1.

**4. The kept-set precision arms cost more than D28 said.**
- Each runs the whole deep path on the dev split (≈ $0.048). `piece=200:kept` and `piece=400:kept` together come to
