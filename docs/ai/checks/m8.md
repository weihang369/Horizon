`horizon eval smoke` (the in-process fake) had written 55 fake answers into `data/cache` on 2026-10-11, and the first
summary run served one of them as real (`sum_en_01` came back as the old synthetic summary). A test-mode run now never
reads or writes the store; the 55 entries were moved out to `data/cache-quarantine-fake-2026-10-11/`. The report's
"store hits" also counted the wrong thing (0 while 312 answers came from the store); it now reads the store.

### Temperature: 1.3 collapsed long chats (design D34, the user's choice)

The first `long` run (`agent`, temperature 1.3, $0.1001 against a $0.0628 estimate) and one `naive` transcript
($0.0212) both drifted into word salad: by turn 35–45 in English, earlier in Malay ("Every-soft-level. Here's route
drawn: last hour there-along-before clock sense…"). 32–47 % of replies were cut off at `max_tokens`, against C4's
2 % target, and the cut-off text fed the slide. Malay recall was 0/5.

The user approved a small test: the English 1:1 script, 50 turns, `agent`, with `--seed-dir` pointing at a copy of
the seed whose `reply.chat` temperature and 1:1 cap were changed.

### Cache hit below X6's 80 %: provider-side, not our prefix

The `long` runs reported a provider cache hit of 31–54 % (English, group) and 94 % (Malay), against X6's ≥ 80 %. The
offline probe ($0, fake provider, six `agent` turns) shows each request is **exactly the previous request plus the new
lines**: nothing earlier changes, and no tail message sits between turns. So the prefix the cache needs is there.
DeepSeek's disk cache is best-effort and is built a few seconds after a request; the eval drives turns back to back,
seconds apart, which likely outruns it (the Malay run, whose turns were slower, hit 94 %). **No change in M8.** M15's
latency suite measures the cache hit at human pacing; if it stays low there, that is the time to look at provider
routing.
